## Как это работает (простыми словами)

1. На диске два слота для системы: A и B. В каждом — `/usr` (erofs),
   хеш-дерево dm-verity и подпись корня хеша. Работает один слот, второй
   свободен.
2. Корень хеша вписан в UKI (ядро + initrd + строка запуска одним файлом).
   Каждая версия UKI грузит только «свой» `/usr`: systemd находит разделы
   по UUID, выведенным из хеша. Любой изменённый байт в `/usr` — ошибка
   чтения.
3. Обновление: `systemd-sysupdate` качает с сервера `/usr`, хеш-дерево,
   подпись и UKI новой версии, пишет разделы в свободный слот, а UKI кладёт
   в ESP с пометкой «3 попытки» (`devuz_<версия>+3.efi`).
4. После перезагрузки systemd-boot берёт новейшую версию и уменьшает
   счётчик. Дошли до `devuz-ready` — `systemd-bless-boot` снимает счётчик,
   версия «хорошая». Не дошли — `devuz-ready` перезагружает машину
   (`FailureAction=reboot`). После третьей неудачи UKI помечен `+0-3`, и
   systemd-boot сам грузит прошлую версию.

## Что поменялось против плана и почему

1. **`+&c` в mkosi v27.1 описан в man, но не реализован в коде.** Man
   обещает дописывать счётчик попыток к имени UKI, если в образе есть
   `/etc/kernel/tries`. В коде v27.1 этого нет (проверено по исходникам
   тега). Поэтому `+3` вписан прямо в `UnifiedKernelImageFormat=%i_%v+3`.
2. **`dracut` — из зависимости ядра.** У `linux-image-7.2.11+deb13-amd64`
   зависимость `dracut | initramfs-tools | linux-initramfs-tool`, apt
   брал первый вариант. Пустой пакет `devuz-no-initramfs` с
   `Provides: linux-initramfs-tool` закрывает зависимость (initrd всё
   равно собирает mkosi).
3. **Ядро: локальный репозиторий mkosi сильнее backports.** mkosi кладёт
   пакеты из `mkosi.packages/` в свой репозиторий с приоритетом 1100,
   наше закрепление backports — 900. Поэтому отдельное закрепление версии
   не понадобилось: что лежит в Release, то и ставится.
4. **`kernel.yml` — единственный workflow с правом записи.** Право
   `contents: write` есть только у него, он не собирает образ и не
   запускается на PR. Настройку репозитория «Workflow permissions: read»
   трогать не пришлось.
5. **UUID разделов — в именах файлов на сервере.** systemd по `usrhash=`
   ищет разделы по UUID из хеша, поэтому sysupdate должен создать разделы
   ровно с такими UUID. `tests/publish-update.py` берёт UUID из образа и
   называет файлы `devuz_<версия>_<UUID>.<тип>.raw` (шаблон `@u`).
6. **Сервера обновлений пока нет.** В `/usr/lib/sysupdate.d` стоит
   заглушка `https://updates.devuz.invalid/os/` (`.invalid` — заведомо
   несуществующий адрес). Тест подменяет его через `/etc/sysupdate.d`.
7. **Подпись обновлений не проверяется — только в тесте.** Тест запускает
   `systemd-sysupdate --verify=no`, в самих `.transfer` проверка подписи
   `SHA256SUMS` не выключена. Подписывать будем на неделе 3 вместе с
   Secure Boot.
8. **Подпись корня хеша (`usr-verity-sig`) — тестовым ключом.** Ключ
   генерируется в Actions на лету (`mkosi genkey`) и никуда не сохраняется.
   Ядро пока подпись не проверяет — это неделя 3 (ключ в UKI + Secure Boot).
9. **Тест «битой» версии — в том же образе.** «Битая» V.2 собирается с
   `DEVUZ_TEST_BROKEN=1` (в `mkosi.postinst`: готовность всегда падает).
   Служба `devuz-update-test` лежит в образе, но запускается только строкой
   ядра — как и самопроверка.

## Что не вышло или отложено

- **Задача 6 (образ без root, `/etc` из factory)** — на неделю 3 вместе с
  LUKS2 + TPM: root будет создаваться при первой загрузке и сразу
  шифроваться, делать это дважды незачем.
- **Риск `FailureAction=reboot`.** Если не доходит до готовности и прошлая
  версия тоже, коробка будет перезагружаться по кругу. Для поля нужно
  ограничение (например, после N перезагрузок — остаться в «аварийном»
  экране с кнопкой поддержки). Записано на неделю 8 («Состояние»).
- **`systemd-dissect` в тесте** — всё ещё не сделан; разметку проверяет
  `sfdisk`, verity — самопроверка и `corrupt-usr`.

## Неделя 3: что дальше

- Тестовые ключи Secure Boot в OVMF, подпись UKI (`SecureBoot=yes`),
  проверка подписи корня хеша ядром, подписанный `SHA256SUMS` для
  sysupdate.
- Самопроверка под Secure Boot: строка ядра из SMBIOS игнорируется —
  нужен отдельный тестовый профиль UKI или учётные данные.
- LUKS2 + TPM (swtpm) по подписанной политике PCR 7+11, ключ
  восстановления; root создаётся и шифруется при первой загрузке, `/etc`
  — из `/usr/share/factory` (итоги разведки недели 1).
- Тесты: подменённый UKI не грузится; диск открывается сам, после
  обновления — тоже; с чужим загрузчиком — нет.
