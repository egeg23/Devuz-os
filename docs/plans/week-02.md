# Неделя 2: обновления A/B с откатом

Старт — 02.11.2026, слово владельца: «Погнали неделя 2». Цель из дорожной
карты (`06-roadmap.md` студии, часть А): `/usr` на erofs + dm-verity, A/B,
`systemd-sysupdate` с тестового сервера, счёт загрузок.

**Проверяемый результат недели**: тест в Actions — обновление A→B проходит;
«битое» обновление после 3 неудачных попыток откатывается на A само.

## Задачи

| № | Что | Готово, когда |
|---|---|---|
| 1 | Хвосты недели 1: ядро в GitHub Release (`kernel.lock`, `kernel.yml` с правом записи только у него), убрать `dracut` (пустой пакет `devuz-no-initramfs`) | в манифесте нет `dracut`; ядро в образе = `kernel.lock` |
| 2 | dm-verity для `/usr`: разделы `usr-verity` (+ `usr-verity-sig` — с тестовым ключом, который генерируется в Actions на лету), `usrhash=` в UKI вместо `mount.usr=PARTUUID` | самопроверка видит `/usr` на `/dev/mapper/usr` (verity); испорченный байт в разделе `usr` — ошибка чтения, а не тихая подмена (отдельный тест) |
| 3 | Счёт загрузок: `systemd-bless-boot` + `boot-complete.target`, к нему — `devuz-ready.service`; UKI ставится с счётчиком `+3` | после успешной загрузки у UKI пропадает счётчик (`bootctl` в самопроверке) |
| 4 | `systemd-sysupdate`: определения для UKI и `/usr` (+ verity), источник — тестовый HTTP-сервер прямо на раннере (артефакты версии N+1, `SHA256SUMS`) | тест: из образа N виртуалка ставит N+1, перезагружается в N+1 |
| 5 | Тест отката: «битая» N+1 (служба готовности падает) → 3 попытки → systemd-boot сам возвращает N | тест в Actions зелёный, в журнале видно 3 попытки и загрузку N |
| 6 | Разведка недели 1 → образ без root: `/etc` из `/usr/share/factory`, `alternatives`, PAM, мастер первой загрузки выключен; root создаёт `systemd-repart` при первой загрузке | если успеваем; иначе — неделя 3 вместе с LUKS2 + TPM |
| 7 | Отчёт `docs/week-02.md` | файл в `main` |

## Порядок

1 → 2 → 3 → 4 → 5, каждое — отдельным PR со своим зелёным тестом.
6 — только если 1–5 готовы.

## Где проверяем

GitHub Actions (KVM на раннере есть). Сервер владельца — когда на нём
запустят `claude remote-control`: тогда можно гонять долгие тесты
обновлений там, не упираясь во время раннера.

## Риски

| Риск | Что делаем |
|---|---|
| Опции `systemd-repart`/`sysupdate` в systemd 257 отличаются от ParticleOS (там systemd новее) | сверяем с man 257; чего нет — записываем |
| Подпись verity (`usr-verity-sig`) требует ключа и сертификата в UKI | тестовый ключ — на лету в Actions, в репозиторий не кладём; без Secure Boot ядро подпись не проверяет — это неделя 3 |
| Тест отката долгий (3 перезагрузки) | `TEST_TIMEOUT` побольше, но не больше 15 минут на прогон |
