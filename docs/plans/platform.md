# Платформа DevUz: безопасность для госструктур и магазин приложений

Решение владельца 03.11.2026: «Да, делаем». Документ — основа для недель 5–8
и части Б; меняется через PR, как код.

## Главный принцип

Правила задаёт и проверяет **сама коробка**, а не доверие к разработчику.
Ядро под каждое приложение не переписываем: есть стабильный API с версиями
и манифест прав, из которого коробка сама строит песочницу.

## 1. Госструктуры, медицина: шифрование, изоляция, обмен

### Уже есть (недели 1–4)

- Диск — LUKS2, ключ в TPM (PCR 7 + подписанный PCR 11).
- Грузится только наша подписанная система; `/usr` под dm-verity.
- Контейнеры — только с нашей подписью; образы служб — в `/usr`.
- Работа без интернета; канал поддержки выключен, пока клиент не включит.

### Добавляем

| Что | Как | Когда |
|---|---|---|
| Изоляция приложений | каждое приложение — свой контейнер, свой пользователь (`userns`), без сети по умолчанию, своя база в PostgreSQL, своя папка `/var/lib/devuz/apps/<id>`; seccomp, без привилегий | недели 6–7 |
| Шифрование по слоям | данные приложения / организации — своим ключом поверх диска; TLS внутри коробки (между службами) и наружу; копии — ключом клиента (Restic) | недели 6–7 (копии — 7) |
| Журнал доступа | кто, когда, к каким данным; журнал с защитой от подделки (journald Forward Secure Sealing), выгрузка для проверяющих | неделя 8 |
| Шлюз обмена с внешними базами | приложение не ходит наружу само: только через шлюз; белый список адресов, вход по сертификатам заказчика (mTLS), очередь при обрыве связи, каждая отправка — в журнал; медицина — HL7 FHIR, если его поддерживает система заказчика | недели 6–7 |
| Несколько организаций на одной коробке | своя база, свой ключ, свои права на каждую организацию | часть Б |

### Проверить до первого госзаказчика (юрист, не код)

- Закон о персональных данных (хранение данных граждан в стране) —
  коробка у клиента это закрывает, нужна проверка юриста.
- Требуются ли **национальные сертифицированные алгоритмы** шифрования и
  сертификация продукта — может поменять выбор криптографии.
- Технические требования систем заказчика, с которыми синхронизироваться
  (например, медицинский портал): формат, протокол, сертификаты.

## 2. Магазин приложений: как разработчик понимает, что можно

### Что выдаём мы

1. **API платформы с версиями** (`/v1/…`): ИИ («Ядро»: модели, речь,
   поиск по документам), база (своя схема), файлы (своя папка), бот,
   окно в «Офисе», шлюз обмена. Старые версии API работают дальше; новое —
   новые методы, ядро не переписываем. Правило устаревания: версия живёт
   не меньше 12 месяцев после выхода следующей.
2. **Манифест приложения** (`devuz-app.toml`): что читает и пишет
   (категории данных: обычные, персональные, медицинские), какие модели, в
   какую сеть и через шлюз — куда, место в «Офисе», цена подписки.
3. **Набор разработчика**: документация, `devuz-app check` (проверка
   манифеста и образа), тестовая коробка (тот же образ, на котором тестируем
   мы), примеры приложений.
4. **Правила магазина**: что запрещено (вынос данных мимо шлюза, майнинг,
   сбор лишнего), ответственность, выплаты — 60% от подписки разработчику.

### Что делает разработчик

Пишет приложение (контейнер + манифест), проверяет у себя
`devuz-app check` и на тестовой коробке, отправляет в магазин.

### Что делает коробка

- По манифесту строит песочницу: юнит quadlet, тома, сеть, токен API
  только с объявленными правами. Чего нет в манифесте — физически нельзя.
- Показывает клиенту права до установки; без согласия не ставит.

### Что делаем мы при публикации

- Автотесты на тестовой коробке, проверка манифеста.
- Подпись разработчика + наша подпись (Podman откроет только так).
- Чувствительные права (персональные, медицинские данные, шлюз наружу) —
  ручная проверка.
- Уровень «допущено для госструктур» — отдельная, строгая проверка.

### Лицензии без интернета

Подписанный файл лицензии (коробка, приложение, срок) проверяется на
коробке без связи с нами; продление — через канал обновлений или флешку.
